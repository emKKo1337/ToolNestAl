A PDF has no idea what a paragraph is. It has no concept of a heading, a table, or a bullet list — just a page full of individually positioned characters, each one told exactly where to sit in x/y coordinates and which font to render in. Word documents, by contrast, are built entirely out of structural concepts: paragraphs, styles, heading levels, table cells. Converting one into the other means reverse-engineering structure that was never explicitly stored in the first place — and understanding that gap explains almost everything about why PDF-to-Word conversion behaves the way it does.

## What a DOCX File Actually Is

![DOCX file structure diagram showing it as a ZIP archive containing word/document.xml, styles.xml, and other XML parts, versus a PDF's flat stream of positioned glyphs](/blog/pdf-to-word-pipeline.svg)

A .docx file is not a single binary blob — it's a ZIP archive. Rename any .docx to .zip and unzip it, and you'll find a folder structure: `word/document.xml` holding the actual paragraph and run content, `word/styles.xml` defining heading and paragraph styles, `[Content_Types].xml` declaring what's inside, plus subfolders for embedded media. This format is called Office Open XML (OOXML), and it's the same open standard used by Google Docs and LibreOffice when they read or write .docx files.

A PDF has no equivalent structure. Internally, a PDF page is a content stream of low-level drawing instructions — "place this glyph at this x/y coordinate using this font at this size." There's no `<paragraph>` tag, no `<heading>` tag, no `<table>` tag. Everything a reader perceives as document structure is an *illusion* created by consistent positioning: a paragraph looks like a paragraph because its lines sit close together and share a left margin, not because the PDF says so anywhere.

Converting PDF to Word means going from "flat, positioned glyphs" to "structured paragraphs, headings, and tables" — and that structure has to be *inferred*, not read directly.

## How Text Gets Reconstructed From Raw Positions

The conversion pipeline starts by extracting every text item on every page along with its x/y position, font size, and font name. At that point, it's just a flat list of positioned strings — no lines, no paragraphs, nothing readable yet.

**Step 1 — Group items into lines.** Items are sorted by Y position, then grouped together whenever their Y coordinates fall within a tolerance of roughly half the page's median font size. This handles the natural sub-pixel jitter in real PDFs, where characters on the same visual line are rarely at the exact same Y value.

**Step 2 — Group lines into paragraphs.** Once lines exist, consecutive lines are merged into a single paragraph unless the vertical gap between them exceeds a threshold — a bigger gap signals a paragraph break, a blank line, or a section boundary.

**Step 3 — Detect headings and emphasis.** The median font size across the whole document is treated as "body text." Any line sized noticeably larger than that median gets classified as a heading (H1, H2, or H3, scaled by how much larger it is). Bold text is inferred from the font name itself — PDFs often embed subset fonts named things like `ArialMT-Bold` or `Calibri-Black`, and matching against `bold`, `black`, or `heavy` in that name is a reliable enough signal without needing to inspect stroke width pixel by pixel.

**Step 4 — Detect tables.** When several consecutive lines share three or more consistent X-coordinate boundaries — meaning text keeps starting at the same handful of horizontal positions, line after line — that's treated as a table, and the shared X boundaries become column boundaries.

None of this is stored in the PDF. All of it is inferred from geometry.

## What Survives the Conversion — and What Doesn't

![Comparison table showing what PDF to Word conversion preserves versus what it cannot reproduce: text and structure preserved, images and vector graphics lost, multi-column layouts linearized, fonts substituted](/blog/pdf-to-word-preserved.svg)

| Element | What happens |
|---|---|
| **Body text** | Extracted accurately and placed into proper Word paragraphs |
| **Headings** | Inferred from relative font size, mapped to Word heading styles |
| **Bold text** | Inferred from font name, applied as a bold run in the output |
| **Simple tables** | Reconstructed from aligned text columns into real Word table cells |
| **Embedded images & vector graphics** | Not reproduced — the PDF's drawing instructions for images and shapes aren't converted to Word objects |
| **Multi-column layouts** | Linearized left-to-right, since a PDF has no explicit "this is column 2" marker — a two-column academic paper reads out of order unless it happens to sort correctly by Y then X |
| **Exact fonts** | Not matched precisely — the original font is rarely embedded in a way that maps to something Word can license, so output uses standard substitutes like Calibri or Times New Roman |
| **Scanned (image-only) pages** | Produce zero extractable text, because there's no text to extract — see below |

Two limitations matter most in practice: multi-column layouts and scanned documents.

**Multi-column linearization** happens because the reconstruction sorts text by Y (top to bottom) then X (left to right) — the natural reading order for a single-column page. A two-column layout defeats this: if column 1 and column 2 have overlapping Y ranges, text from both columns interleaves line by line instead of reading column 1 fully before column 2. This is an inherent limitation of any geometry-based reconstruction, not a bug specific to one tool.

**Scanned PDFs** are the more common trap. A scanned page is just a full-page image — a photograph of text, not actual text characters. `getTextContent()` on a scanned page returns nothing, because there is nothing to return: no glyphs were ever placed, only pixels. Converting a scanned PDF without OCR first produces an empty or near-empty Word document, not an error — which is exactly why it catches people off guard.

## Scanned PDFs Need OCR First

If your PDF came from a scanner or a "print to PDF from a photo" workflow, run it through [OCR PDF](/pdf-tools/ocr-pdf) first. OCR (Optical Character Recognition) analyzes the pixels of each scanned page and recognizes actual characters, producing real, selectable text — the same kind of text a natively-created PDF would have had all along. Once that text exists, PDF to Word conversion can extract and reconstruct it exactly like any other document.

A quick way to tell whether a PDF needs OCR: open it in any PDF viewer and try to select a sentence with your cursor. If nothing highlights, or the whole page highlights as one image, it's scanned — OCR it before converting.

## Common Mistakes

**Mistake 1: Converting a scanned PDF without running OCR first.** The result looks like conversion silently failed — an empty or nearly empty document — when really there was no text to extract in the first place.

**Mistake 2: Expecting pixel-perfect layout preservation.** PDF to Word conversion reconstructs *structure* (paragraphs, headings, tables), not an exact visual replica. If you need the PDF to look identical, keep it as a PDF; convert to Word when you need to *edit* the content, not preserve the exact layout.

**Mistake 3: Converting complex multi-column academic papers or magazine layouts and expecting correct reading order.** Two- and three-column layouts are a known weak point for any geometry-based converter, since the PDF format itself doesn't mark which column text belongs to.

**Mistake 4: Assuming embedded charts, diagrams, or photos will carry over.** They won't — only text and simple table structure convert. If your document is mostly images, you'll get an editable text shell with the visual content missing.

## Frequently Asked Questions

### Why doesn't my converted Word document look exactly like the PDF?

Because PDF and Word represent documents completely differently. A PDF stores exact pixel positions for every character; Word stores structural paragraphs, styles, and flowing text. Conversion reconstructs structure from the PDF's positioning data, but it can't reproduce an exact visual layout — the goal is an *editable* document, not a pixel-identical copy.

### Why is my converted document empty or missing most of the text?

Your original PDF is almost certainly a scanned document — a photograph or scan saved as a PDF, where each page is one image rather than actual text characters. There's nothing for a converter to extract in that case. Run the file through an OCR tool first to recognize the text, then convert the OCR'd result to Word.

### Will my images and charts transfer to the Word document?

No. Browser-based PDF-to-Word conversion focuses on text, headings, and simple tables. Embedded images, vector graphics, and charts are part of the PDF's drawing instructions, not its text content, and aren't reproduced in the output document.

### Why did a two-column PDF convert with text in the wrong order?

Because a PDF has no explicit marker for "this text belongs to column 2." Reconstruction sorts text primarily by vertical position, which works perfectly for single-column pages but can interleave two columns that overlap vertically — producing text that reads left column, right column, left column again instead of column 1 fully, then column 2.

### Why is the font different in my converted document?

The exact font used in the original PDF is rarely available in a form the converter can reuse — many PDFs embed only a subset of a font's glyphs, licensed for display only. Rather than guess, the converter substitutes a standard, widely available Word font (typically Calibri or Times New Roman) so the document opens correctly on any machine.

### How are headings detected if the PDF doesn't mark them?

By comparing each line's font size to the median font size across the whole document. Text sized noticeably larger than the body-text median is classified as a heading — the bigger the difference, the higher the heading level (H1, H2, or H3). This works well for typically formatted documents but can misfire on PDFs with unconventional typography.

### Is my PDF uploaded to a server during conversion?

No. The entire pipeline — text extraction, structure reconstruction, and DOCX generation — runs in your browser using JavaScript libraries (pdfjs-dist and docx). Your file never leaves your device.
